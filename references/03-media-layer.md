# 03 · 媒体层

> 媒体在本 skill 里**默认全部包含**（图片 / 视频 / 文件 / 动画表情），不单独向用户询问。
>
> 本篇给的是路径、格式、坑与**最小验证片段**。完整实现由执行本 skill 的 AI 依本文档完成。

## 总览：媒体是怎么被找到的

消息库里只有消息，媒体文件在磁盘另一处。两者之间靠一张映射表连起来：

```
Msg_<md5(会话名)>.db                 消息表，local_type 标识类型
      ↓ (chat_id + local_id + create_time)
message_resource.db → MessageResourceInfo
      ↓ packed_info（protobuf）
   field 2 = 嵌套 message，其 field 1 = 32 位存储哈希
      ↓ 哈希即文件名
msg/attach/<md5(会话名)>/<消息月份>/Img/<哈希>.dat      图片
msg/video/<月份>/<哈希>.mp4                            视频
msg/file/<月份>/<文件名>                               文件
```

**先做映射，再谈解密。** 没有映射就不知道哪个文件属于哪条消息。
映射做错的表现是「图片能解出来，但张冠李戴」。

**映射范围要收窄**。全量映射动辄十万条，只为用户实际要看的会话做映射即可。
范围直接读业务库里的「特别关注」标记，用户以后加关注对象重跑映射就能跟上。

## 一、图片

### 1.1 附件后缀与候选顺序

同一张图在 attach 目录下可能有多个副本，**后缀决定用途**，取错就永远显示糊图：

| 后缀 | 含义 |
|---|---|
| `.dat` | 原图，清晰度最高，**优先取用** |
| `_h.dat` | 高清缓存，**存在损坏文件**（段链在 SOS 前断裂、无 EOI），须过校验 |
| `_t.dat` | 缩略图（约 180×103），仅兜底 |
| `_W.dat` / `_t_W.dat` | 2023-12 ~ 2025-06 的旧版 wxgf 容器，2026 年后不再产生 |

**候选顺序必须是 `.dat` > `_h.dat` > `_t.dat`。**
顺序写错的后果：缩略图抢先命中，页面永远显示糊图，而且看不出哪里错了。

**查解密缓存时必须用同一个顺序**，否则缩略图会被当成原图缓存下来，之后一直命中错的那份。

### 1.2 图片容器（V2 格式）

4.x 的图片容器结构（头 15 字节）：

```
<6s magic><u32 aes_size><u32 xor_size><1 pad>
magic = 07 08 56 32 08 07      即 "\x07\x08V2\x08\x07"
```

整体布局：

```
header(15)
+ AES-128-ECB（body[0:aes_size]，PKCS7 填充）
+ 16 字节固定分隔符
+ 单字节 XOR（尾部 xor_size 字节，每字节与同一个 key 异或）
```

解出来若是普通图片，`detect` 头部魔数即可判断格式（`FFD8FF` = JPEG、
`89504E47` = PNG、`RIFF....WEBP` = WebP、`GIF8` = GIF）。

解出来若以 `wxgf` 开头，说明落在微信私有容器里，见 1.4。

### 1.3 「xorSize 字段不可信」

**这是最容易踩的一个坑**：大文件里该字段固定写成 1048576（1MB），与实际不符。

正确做法：**XOR 区一直解到文件末尾，再把尾部元数据裁掉**。
按该字段截断，结果是所有大图都解不出来，而小图正常——现象很迷惑。

### 1.4 wxgf 容器

`wxgf` 是微信的私有 HEVC 容器，**静态图也用它存**，必须经微信自带的解码能力还原：

```
<微信安装目录>\<版本>\VoipEngine.dll
导出函数：wxam_dec_wxam2pic_5
```

2026 年实测：某库 3918 条图片消息中有 123 条为 wxgf。不处理它，这部分图永远开不出来。

**调用外部进程必须用异步方式**。Windows 上同步调用（`spawnSync`）会报 EBUSY，
而且异常容易被静默吞掉——表现是「解码看起来成功，实际全部失败」，排查很久才发现。

两个配套的工程细节，不做会反复出问题：

- **同一份数据并发去重**：同一张图可能被多个请求同时触发解码。
  用「数据哈希 → Promise」的映射让它只解一次，其余请求共用同一个结果；
- **失败重试一次**：`VoipEngine.dll` 有 20MB 左右，高频连续调用时偶发加载失败，
  失败后隔 100~200ms 再试一次即可，不要直接放弃。

### 1.5 图片密钥

**图片密钥与数据库密钥是两套完全不同的东西**（形态、来源、校验方式都不同，
对照表见 `02-data-layer.md` 第 2 步开头）。用数据库密钥去试图片，全都对不上。

**路径一：内存扫描（先用这个）**

四步，缺一不可：

1. **反推 XOR key**：找 attach 目录下最近的 `*_t.dat`，确认头部是 V2 魔数；
   读文件**最后 2 字节**，取出现最多的那个值 `t`，则 `XOR key = t ^ 0xFF`。
   （原理：JPEG 尾部固定是 `FF D9`，用它的加密结果反推）
2. **取已知密文块**：任取一个 V2 文件的 `bytes[15:31]`（16 字节），作为校验用的密文。
3. **扫内存**：正则搜**纯字母数字串** ——
   `(?<![a-zA-Z0-9])[a-zA-Z0-9]{32}(?![a-zA-Z0-9])`，同时也试 16 位的版本。
4. **校验**：把候选当 AES-ECB 密钥去解第 2 步的密文，解密结果命中图片魔数
   （`FFD8FF` JPEG / `89504E47` PNG / `RIFF` WebP / `wxgf` / `GIF8`）即为正确密钥。

首次找不到很正常——**先在微信里点开 2~3 张图片**让密钥进入内存，再重跑。
适合做成持续扫描的脚本（每隔几秒扫一次，命中即落盘）。

**路径二：派生（可用于交叉验证）**

```
AES key = md5(account_seed + wxid)[:16]
```

`account_seed` 是账号级常量，**藏在微信主进程内存里**，取法是：
在内存里搜 **5–20 位纯数字串**（ASCII 与 UTF-16 两种编码都要试），
拿 `md5(seed + wxid)[:16] == 路径一得到的图片密钥` **反推验证**——
用已知答案去找 seed。命中后缓存复用。

两条路径的结果应当一致，可互相印证。

### 1.6 能力边界（解释「为什么有些图看不到」）

这条要主动向用户说明，否则他会以为程序坏了：

- 缩略图在**收到消息时就存在**（约 16KB / 210×157）；
- 原图**需在微信客户端点开该图，微信才会下载到本机**；
- 缩略图像素不足，**无法还原成高清**——放大属于猜测；
- 未点击查看的图片由系统自动保留 **14 天**，超期失效；
- 已点开的仅缓存在**当前设备**，各设备缓存互相独立（手机端点开不会让电脑端拿到原图）。

结论：**补图只能在电脑端微信里点开对应图片**，之后刷新即可。

### 最小验证片段

校验解出来的图片是不是完整的（**不要只看文件头通过就算成功**）：

```python
def is_complete_jpeg(b: bytes) -> bool:
    """JPEG 段链必须走到 SOS 且有 EOI，才算完整。"""
    if b[:3] != b"\xff\xd8\xff":
        return False
    i, n = 2, len(b)
    while i + 4 <= n:
        if b[i] != 0xFF:
            return False
        marker = b[i + 1]
        if marker == 0xDA:            # SOS，之后是压缩数据
            return b.rstrip().endswith(b"\xff\xd9")   # 必须有 EOI
        if marker in (0xD8, 0x01) or 0xD0 <= marker <= 0xD7:
            i += 2
            continue
        seg_len = int.from_bytes(b[i + 2:i + 4], "big")
        i += 2 + seg_len
    return False
```

判读标准：`True` = 完整原图；`False` = 半张图或缩略图，说明截断或候选取错。
PNG / WebP / GIF 同理，改查各自的结束标记。

## 二、动画表情（local_type=47）

**存放**：消息 `content` 里是 JSON，形如
`{"emoji":true,"md5":"<32位>","emojiType":1}`，`media_path` 存 md5。
同一表情被多人多次发送时 md5 相同，**按 md5 去重后批量处理**。

**加密**：AES-128-CBC + PKCS7，且 **key 与 IV 相同**。

```
key = md5(account_seed + wxid + "EMOTICON")[:16]
```

**限制**：微信只保留最近约 3 个月的表情缓存，历史表情本地没有密文；
CDN 直链对历史消息返回 403。**历史表情无法离线补全**，
除非在微信里重新翻看触发缓存。这条要提前告知用户。

**最小验证片段**：解出后检查是不是 GIF（`GIF87a` / `GIF89a`）。
不是 GIF 说明 key 或 IV 用错了。

## 三、视频（local_type=43）

**存放**：`<数据根>\<账号>\msg\video\<月份>\<32位hex>.mp4`，**明文，可直接播放**。
同目录另有 `<hex>_thumb.jpg`（首帧）与 `<hex>.jpg`（封面）。

**映射**：与图片同构，取 `MessageResourceInfo` 中 `message_local_type = 43` 的记录，
`packed_info` 里的 32 位 hex 即文件名。

**播放接口必须支持 HTTP Range**。不支持的话视频能播但**进度条拖不动**，
用户会以为是视频坏了。Range 要正确返回 `206 Partial Content`、`Content-Range`、`Accept-Ranges`。

**限制**：与图片同机制——**未在客户端播放过的，本地没有 mp4**。
这种情况退回首帧缩略图 + 时长，并标注「未缓存」。

**最小验证片段**：检查 `ftyp` box 判断是不是合法 MP4。

```python
with open(mp4, "rb") as f:
    head = f.read(12)
print(head[4:8])    # 应为 b'ftyp'；对不上说明文件不完整或是占位文件
```

## 四、文件消息（local_type=49 且 `<type>6</type>`）

**存放**：`<数据根>\<账号>\msg\file\<月份>\<文件名>`，**明文，保留原始文件名**。
按扩展名判断类型：docx / xlsx / pptx 是 ZIP（`PK\x03\x04`），
xls 是 OLE2（`D0 CF 11 E0`），pdf 是 `%PDF`。

### 最容易踩的坑：文件名里的 HTML 实体

消息 XML 的 `<title>` 常把空格写成 `&#x20;`。**实测某库 1283 条中 126 条受影响**。

不解码的后果：拼出的路径与磁盘上的真实文件名对不上，接口一律 404，
而且日志里看不出问题在哪——文件名「看着是对的」。

处理规则：**`<title>` 要做 HTML 实体解码；CDATA 里的内容按原样取，不做实体转义**。
两条规则相反，别写反。

**打开方式**：Office 类文件浏览器渲染不了，交给**系统默认关联程序**打开。
实现里不要写死具体应用名——取决于使用者本机的文件关联，可能是 Microsoft Office、WPS 或 LibreOffice。

**限制**：同样受「微信未下载到本机则无文件」约束。实测某库 1283 条文件消息中
本地可打开 487 条（38%）。

**最小验证片段**：按解码后的名字去磁盘上找，找得到才算对。

```python
import os, html
name = html.unescape(title_from_xml)      # 关键：先解码
p = os.path.join(file_dir, name)
print("命中:", os.path.exists(p), "| 文件名:", name)
```

## 五、视频号分享卡片（local_type=49）

`<title>` 里是占位文案（「当前微信版本不支持展示该内容」），**真实信息在另外两个节点**：

| 节点 | 场景 | 关键字段 |
|---|---|---|
| `<finderFeed>` | 作品 | nickname / desc / coverUrl / avatar / objectId |
| `<finderLive>` | 直播 | 同上 |

### 坑：CDATA 整体包裹

字段值常被 `<![CDATA[...]]]]><![CDATA[>` 这样成对包裹。**解析前必须先剥离 CDATA**。
不剥离的后果：`objectId` 会带上方括号，导致封面接口的 id 校验失败，
最终静默退回占位图，看起来像「这张卡片没封面」。

### 坑：封面地址会过期

封面是腾讯 CDN 的 http 地址，带 `encfilekey`，**会过期**。
做法是服务端按需下载并缓存到本地，且**只允许腾讯域名**。

> 这一处是媒体层里唯一的网络请求，读的是腾讯公网 CDN 上的公开封面图，
> 不上传任何本地数据、与微信本地文件无关。向用户说明时要讲清楚这一点。

**最小验证片段**：解析后打印昵称与 objectId，人工比对是否与卡片内容相符。

## 六、渲染层的缓存陷阱

这两个坑会让你「明明修好了，页面还是旧的」，极耗排查时间：

| 现象 | 原因 | 处置 |
|---|---|---|
| 解码逻辑修好了，页面还是糊图 | 浏览器吃了旧的 HTTP 缓存 | 媒体 URL 必须带版本号（如 `&v=<服务启动时刻>`） |
| 在微信点开原图后，页面仍显示缩略图 | 缩略图响应带了长缓存 | **缩略图响应必须 `no-cache`**；原图可长缓存 |

原则：**会随本地文件变化而变化的资源，不能带长缓存**。

## 七、逐类自查表

媒体做完后逐项过一遍，不要只看「有图出来」就算通过：

| 类型 | 抽查什么 | 通过标准 |
|---|---|---|
| 图片 | 各抽一张普通 JPEG、一张 wxgf | 完整原图（段链到 EOI），尺寸明显大于缩略图 |
| 表情 | 抽一个近 3 个月内的 | 是 GIF，能循环播放 |
| 视频 | 抽一条已播放过的 | 能播、**进度条能拖** |
| 文件 | 抽一条名字里带空格的 | 按解码后文件名能打开 |
| 视频号 | 抽一条作品卡片 | 昵称、文案、封面都对 |
| 边界 | 抽一条「未缓存」的 | 显示占位 + 提示，而不是空白或报错 |
