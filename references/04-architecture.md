# 04 · 架构选型

> 七问答完之后读本篇。给的是**结构与取舍理由**，不含业务代码。

## 顺序原则

按这个顺序定，反过来做往往要返工：

```
需求（Q3）→ 数据流 → 数据落位 → 技术栈 → 目录骨架
```

先挑框架再想需求，会做出一个用不上的东西。

---

## 一、三条主线的数据流

### A 检索浏览型

```
微信库 → 提取 → 本地库 → 会话列表 / 时间线接口 → 前端媒体渲染
                                    ↓
                              媒体按需解密 + 缓存
```

**重心**：查询要快（分页、按时间索引），媒体要按需解（不能开页面就全解）。
**最容易做错**：一次性把所有媒体解密，首次加载等到用户放弃。

### B 联系人管理型

```
微信库 → 提取 → 本地库 → 规则计算（多久未回、谁待跟进）→ 仪表盘 / 提醒
                       ↓
                  档案 · 标签 · 台账导出
```

**重心**：状态计算要准（时区、会话归属、自己人与他人的区分）。
**最容易做错**：把「计算派生状态」和「存储原始消息」混在一处，导致每次打开都全表扫描。

### C 内容分析型

```
微信库 → 提取 → 本地库 → 应用消息解析（type=49 等嵌套结构）→ 结构化记录 → 统计 / 报表
```

**重心**：解析规则要可回溯（一条记录能追回原始消息），口径要唯一。
**最容易做错**：同一指标在两处用不同口径算，越用越不可信。

### 默认形态（Q3 未作答时）

取 A 的骨架做精简版：

- 会话列表 + 时间线浏览 + 媒体渲染
- 加一个简单看板页（今日消息数、最近活跃会话）
- **不做**提醒引擎、不做报表、不做导出——这些等用户看到实物后再提

范围严格限定在 Q4、Q5 选定的范围内。媒体按默认全包含处理。

---

## 二、数据落位

数据放哪，直接决定后面备份、迁移、打包的麻烦程度。

| 方案 | 位置 | 优点 | 代价 |
|---|---|---|---|
| **项目内 `data/`** | 与代码同级 | 迁移方便，一个目录搬走即可 | 备份 / 打包 / 统计类逻辑**必须显式排除它**，否则会连带数据甚至自我递归 |
| **项目外独立目录** | 如 `D:\某工作台数据\` | 数据与代码彻底分离，备份清晰 | 程序移动后要重新指路，靠配置文件维系 |
| 系统目录（AppData 等） | 用户配置区 | 符合部分平台习惯 | 会被清理工具误删；数据重要时不建议 |

**两条硬要求**：

1. **数据目录由单一配置文件指定**（如项目内一个 `data-path.txt` 或配置项），
   禁止在多个文件里各写一份路径；
2. 选了「项目内」这一档，就要有一套明确的排除规则，并且**按相对路径匹配**——
   用条目名匹配多级路径（如 `server/public` 这种）永远匹配不上，是个隐蔽的坑。

## 三、技术栈取舍

### 后端

| 方案 | 适合 | 代价 |
|---|---|---|
| **轻量 HTTP 服务**（Fastify / Express 等） | **推荐**。需要按需解密媒体、增量同步、多页面接口 | 要管进程与端口；要处理「服务没起来」的报错 |
| 纯静态 + 预导出 JSON | 只读展示、数据一次性导出 | 不能增量更新，不能按需解密，媒体只能预生成 |
| 桌面壳（Electron 等） | 想要双击即用的桌面观感 | 体积大、构建链长。与「不过度成品化」的取向也不合 |

### 数据库

| 方案 | 适合 | 代价 |
|---|---|---|
| **Node 内置 SQLite** | **推荐**。零外部依赖，开箱可用 | 需要较新的 Node 版本 |
| better-sqlite3 等第三方绑定 | 生态成熟、API 顺手 | 需要本地编译，Windows 上常要构建工具链 |
| sql.js / 纯 JSON 文件 | 无原生依赖 | 数据量一大就明显变慢；JSON 每次全量读写 |

选型建议：**先能跑通，再谈优化**。首次搭建用内置方案，遇到瓶颈再换。

### 前端

| 方案 | 适合 | 代价 |
|---|---|---|
| **Vue3 + Vite** | **推荐**。生态好，构建产物可由后端直接托管，省去第二个服务 | 需要构建步骤（改完源码必须重新构建才生效） |
| 原生 HTML + 少量 JS | 页面少、交互简单 | 组件复用差，页面一多就乱 |
| React / Svelte 等 | 团队已有偏好 | 与 Vue 无本质差异，按熟悉度选即可 |

**风格来源**：见 `05-frontend-layout.md`，那里给视觉风格资源的清单与选用方法。

## 四、目录骨架

按职责分，不按技术分。这是推荐的形状（名称可换，分层不要换）：

```
<项目>/
├── server/                服务端
│   ├── index.js           入口：接口注册 + 静态资源托管
│   ├── config.js          读配置（唯一真相源）
│   ├── routes/            接口层：只读业务库，不做重计算
│   ├── sync/              同步层：导入消息、媒体映射与解密
│   ├── db/                连接与结构迁移
│   └── public/            前端构建产物（由后端托管）
├── web/                   前端源码
│   └── src/
│       ├── pages/         页面
│       └── styles/        样式与设计令牌
├── wechat-extract/        数据获取（Python 侧）
├── data/                  数据目录：业务库 + 媒体缓存
└── data-path.txt          数据目录指向
```

**分层职责**（这条比目录名重要）：

| 层 | 该做 | 不该做 |
|---|---|---|
| `wechat-extract` | 从微信到本地的一次性与增量搬运 | 不掺业务逻辑 |
| `server/sync` | 导入业务库、做媒体映射、按需解密 | 不实现页面逻辑 |
| `server/routes` | 读业务库、返回结构化数据 | 不做重量计算 |
| `web` | 调接口、渲染 | 不直接读本地文件 |

分层的价值在排查：出问题时能一眼定位是搬运错了、导入错了，还是显示错了。

## 五、接口约定

四条，前两条是硬约束：

1. **只读微信目录**。全程不对微信数据做任何修改——不写入、不改动、不删除、
   不改微信设置、不注入微信进程。只读副本。
2. **单一配置文件作真相源**。数据目录、账号、时间范围集中一处，
   缺字段时抛明确的中文错误并给出修复命令，不要让它变成下游的「文件找不到」。
3. **媒体按需解密 + 缓存**。打开页面只解当前视口需要的，解过的缓存起来。
4. **媒体 URL 带版本号**，缩略图类资源不带长缓存（详见 `03-media-layer.md` 第六节）。

## 六、何时该收手

有些需求看起来合理，但本机数据做不到。**明说做不到**，不要含糊地开始，否则多半做到一半就卡住：

| 需求 | 为什么做不到 |
|---|---|
| 微信一有消息就实时更新 | 本地库是快照，需要重新提取才能看到新消息 |
| 自动回复 / 代发消息 | 超出只读范围 |
| 手机上看 / 多设备同步 | 数据只在这台电脑上 |
| 还原几个月前没点开过的图片 | 14 天窗口已过，本地没有原图 |
| 拿到别人账号的聊天记录 | 密钥只对应本机当前登录账号 |

对第四条可以给替代方案：让用户在微信里点开该图，之后刷新就能看到。
