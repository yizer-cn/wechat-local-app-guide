# 05 · 界面形态与布局

> Q6（界面风格）与 Q7（功能）有答案之后读本篇。
> 给的是**布局骨架与资源清单**，不含组件代码。

## 顺序原则

```
先定信息结构 → 再定布局 → 最后定视觉风格
```

风格库解决「长什么样」，解决不了「该有什么页面」。跳过前两步直接挑风格，
结果是一套好看的皮包着不合适的骨架。

Q6 用户答不上来时，**不要在这里追问**。等数据层跑通、拿到真实的数据形态
（会话数、消息量、媒体占比）之后再推荐，理由见 `03-media-layer.md` 与 SKILL.md 3.1。

## 一、默认三项功能的布局骨架

### 1.1 仪表盘看板

回答一个问题：**打开先看什么**。

```
┌──────────────────────────────────────────────┐
│ 顶栏：今日概览（消息数 / 活跃会话数 / 待处理） │
├───────────┬──────────────────────────────────┤
│ 导航栏    │ 最近活跃会话（按最后消息时间倒序）│
│ (固定)    │ ───────────────────────────────  │
│           │ 待处理项卡片（可点击跳转）        │
└───────────┴──────────────────────────────────┘
```

要点：

- 指标卡控制在 **4~5 个**，再多就失去「一眼看整体」的效果；
- 每张卡都要能点进详情，只展示不可交互的卡片价值很低；
- 导航固定、主区独立滚动（侧边栏固定布局）。窄屏（<1024px）收成抽屉或图标条。

### 1.2 时间线翻记录

```
┌───────────┬──────────────────────────────────┐
│ 会话列表  │ 消息流（按时间）                  │
│ 可搜索    │  ─ 文本 / 图片 / 视频 / 文件卡片  │
│ 可筛选    │  ─ 点击图片开灯箱                 │
│           │  ─ 加载更多 / 虚拟滚动            │
└───────────┴──────────────────────────────────┘
```

要点：

- **虚拟滚动或分页**必须做。消息上千条全量渲染，页面会卡到不可用；
- 灯箱要支持**方向键与滚轮翻页**，并有张数指示；滚轮翻页要节流（触控板会连发事件）；
- 媒体**懒加载**：只解当前视口需要的，滚动到再解；
- 长文本消息要处理换行与折叠，避免一条消息占满整屏。

#### 消息怎么加载（这里踩过坑）

**展示顺序用正序**：最旧在上、最新在下，打开时定位到最新。
这与微信本身的阅读习惯一致；反过来（最新在上）会让「顺着上下文往下读」变得别扭。

**首次加载后必须滚动到底部**——这是实际踩过的坑。少了这一步，
打开会话看到的是**最旧的那批消息**，用户会以为消息没加载出来。
做法：数据渲染完成后，把滚动容器定位到最底部。

**分页用游标，不要用 offset**。游标即消息时间戳：

```
取最新一页：ORDER BY msg_time DESC LIMIT 200   →  反转成正序后返回
加载更早：  WHERE msg_time < <当前最旧一条的时间>
            ORDER BY msg_time DESC LIMIT 200
是否还有更多：返回条数 == 每页条数
```

**为什么不用 offset**：增量同步会往库里插入新消息，offset 随之错位，
表现为翻页时出现重复条目或整段漏读。游标基于时间戳，不受插入影响。

**「加载更早」要 prepend，并且补偿滚动位置**。新内容插到列表头部会把可视区往下推，
用户眼前会「跳」一下。做法：插入前记录滚动高度，插入后把差值补回去，视口就稳住了。

**每页条数**：200 条是验证过的合适值——太少导致频繁翻页，太多拖慢首次加载。

**灯箱的翻页范围**取「当前已加载的消息」里的图片，按时间顺序。
点「加载更早」后集合自动扩大，不需要单独维护一份全量图片索引。

### 1.3 每日报告

```
┌──────────────────────────────────────────────┐
│ 日期选择 / 上一份 · 下一份                    │
├──────────────────────────────────────────────┤
│ 报告正文（结构化：讨论了什么 / 涉及谁 / 待办）│
│                                              │
├──────────────────────────────────────────────┤
│ 导出（Markdown / 复制）                       │
└──────────────────────────────────────────────┘
```

#### 呈现逻辑

报告页的价值在**可读**，不在完整。三条原则：

1. **默认只呈现前一天**。报告适合固定节奏使用（每天看一份），
   做成「全历史汇总」既慢又没人读；
2. **按主题分块，不按时间罗列**。一天几百条消息逐条列出没有价值，
   读者要的是「发生了什么」；
3. **不堆砌统计数字**。消息条数、发言排名这类指标缺少行动价值，
   放上去只会让报告变长。

一个可参考的结构：

```
## 每日报告 · <日期>

### 讨论了什么事
- <事项>：<一两句说明>（涉及：<人>）

### 谁在找我，我还没回
- <人> · <时间> · <一句话>

### 待办与约定
- <事项>（约定时间：<…>）

### 无法归类的消息
- <条数> 条（可展开）
```

几处细节：

- **每块都要有「涉及谁」**，否则读者无法判断要不要跟进；
- **要能追溯**：报告里的每条最好留一条回到原消息的路径；
- **要能导出或复制**：用户常把报告拿去别处用（发群、存笔记）；
- **日期切换不要整页重载**，否则逐日翻看的体验很碎；
- **归不了类的消息单列一块，不要丢弃**——丢掉会让用户怀疑「是不是漏了什么」，
  而这种怀疑一旦产生，报告就不可信了。

## 二、可选扩展与其布局影响

| 扩展 | 加在哪 | 注意 |
|---|---|---|
| 表格台账 | 独立页 | 列多时横向滚动，首列固定 |
| 提醒 | 全局顶栏横幅 | 必须在任何页面都能看到 |
| 全文搜索 | 顶栏搜索框 + 结果页 | 结果要显示上下文片段与来源 |

**常见错配**（这些组合看起来合理，用起来别扭）：

| 错配 | 问题 |
|---|---|
| 用看板形态做检索 | 看板强调概览，翻查具体消息需要的是列表 + 搜索 |
| 用表格形态做时间线 | 聊天的价值在上下文连贯，表格切断了它 |
| 三样都做在一个页面 | 一屏塞三套信息结构，结果哪个都不好用 |

## 三、视觉风格资源

**先定信息结构，再从这里挑风格。** 两份资源各有分工：

### 3.1 stylekit（外部，风格库）

- 地址：`github.com/AnxForever/stylekit`
- 内容：约 148 套视觉风格，每套含设计令牌、组件配方、硬性约束与提示词
- 两种接入方式：
  - 作为 Agent Skill：`AnxForever/stylekit-skill`
  - 按 shadcn registry 引入单套风格

**适合场景**：用户说不出风格、或想要一个明确的方向。挑一套风格，产出会稳定很多，
不会每次都要重新猜「好看」是什么。

**挑法**：按工作台的用途挑「信息密集、克制」那一类，别挑展示型风格——
数据工具不需要视觉冲击，需要长时间看不累。

### 3.2 impeccable（本机若已安装）

前端设计方法库，30 篇分册，按场景读对应篇目。与本场景相关的挑法：

| 场景 | 读哪篇 |
|---|---|
| 定布局与空间节奏 | `arrange.md`、`spatial-design.md` |
| 信息密集界面降噪 | `cognitive-load.md`、`distill.md`、`quieter.md` |
| 排版与字号层级 | `typography.md`、`typeset.md` |
| 配色与对比度 | `color-and-contrast.md`、`colorize.md` |
| 交互与状态反馈 | `interaction-design.md` |
| 动效（克制使用） | `motion-design.md`、`animate.md` |
| 窄屏适配 | `responsive-design.md` |
| 空状态与首次使用 | `onboard.md` |
| 边缘情况（长文本、溢出、缺图） | `harden.md` |
| 文案（按钮、提示、报错） | `ux-writing.md` |
| 收尾打磨 | `polish.md`、`normalize.md` |
| 自查评审 | `audit.md`、`critique.md`、`heuristics-scoring.md` |

**用法**：不要一次全读。按当前卡住的环节读对应那一篇。

### 3.3 本机未安装时的替代

两份都拿不到时，仍可以用通用设计原则起步：定好栅格与间距阶（4 / 8 的倍数）、
限定 2 种字体、限定一套中性色 + 一个强调色。这三条能覆盖大部分「看起来不像样」的问题。

## 四、长列表与媒体渲染的实操要点

这几条不做，界面会明显卡：

| 项 | 做法 |
|---|---|
| 长消息列表 | 虚拟滚动；至少要做分页 |
| 图片 | 懒加载 + 缩略图先出（缩略图很小，先显示占位再换原图） |
| 视频 | 不自动播放；点击才加载，且必须支持 Range |
| 文件卡片 | 显示扩展名块 + 文件名 + 大小，点击交给系统程序打开 |
| 灯箱 | 相邻图片预加载；翻页有节流；到头停住不循环 |
| 搜索 | 输入防抖；结果分页 |

**媒体 URL 必须带版本号，缩略图不带长缓存**——这两条是渲染层最容易吃暗亏的地方，
详见 `03-media-layer.md` 第六节。

## 五、反面清单

| 反例 | 为什么不好 |
|---|---|
| 一屏内图文互相覆盖 | 信息互相遮挡，两样都读不清 |
| 硬切场景切换 | 用户会丢失空间感；滑切或淡入更稳 |
| 堆砌动效 | 动效服务于理解，不是装饰。数据工具尤其要克制 |
| 每张卡片都加边框与阴影 | 视觉噪声叠加，重点反而不突出 |
| 空状态只写「暂无数据」 | 要告诉用户下一步做什么 |
| 报错只给错误码 | 要说清发生了什么、用户能做什么 |

## 完成标志

定完这三样，就可以动手搭界面了：

1. 信息结构（有哪些页、每页回答什么问题）；
2. 布局骨架（对齐到上面某一种，或说明为什么自创）；
3. 风格来源（选定具体的一套，或说明用通用原则起步）。

界面搭完，进入 `06-build-and-verify.md` 做逐步验证。
