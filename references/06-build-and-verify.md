# 06 · 每步怎么判断「做对了」

> 这篇是全程都要用的。每完成一步就过一道验收，不要攒到最后一起看。

## 验收总则

1. **不要只读代码就宣称通过**。代码看起来对与结果正确，中间隔着很多变量。
   验收必须有**可观察的证据**：一个数字、一张图、一次实际打开。
2. **每步做完立刻验**。数据层没过就去做界面，出错时会分不清是哪一层的责任。
3. **验收动作要能重复**。把检查写成一个可以随时重跑的脚本或命令，
   改完代码再跑一遍，比人工回忆「刚才验过什么」可靠。
4. **记下证据**。哪一步、什么证据、什么时候。后面出问题要回溯时，这是唯一线索。

---

## 一、数据层验收

### 1.1 密钥正确

解密产物的**文件头**必须是 `SQLite format 3\0`。对不上说明密钥错或保留区没剥干净。

```python
with open(db_path, "rb") as f:
    head = f.read(16)
print(head == b"SQLite format 3\x00", head)
```

### 1.2 表能读出来

```python
import sqlite3
con = sqlite3.connect(db_path)
n = con.execute("SELECT COUNT(*) FROM sqlite_master WHERE type='table'").fetchone()[0]
print("表数量:", n)      # 应为正数
```

### 1.3 数据量与预期相符

统计各表条数，与用户选定的范围比对：

| 检查 | 通过标准 |
|---|---|
| 会话数 | 与 Q4 选定的数量一致 |
| 消息时间范围 | 落在 Q5 选定的区间内，**没有超出的旧数据** |
| 最早 / 最晚一条的时间 | 能对上，不是 1970 或未来时间 |

时间范围这项最容易出问题：范围条件写错会让全量数据混进来，
首次加载慢得莫名其妙，而且不容易发现。

### 1.4 抽一条核对原文

**这一条不能省**。从库里随便取一条消息，去微信客户端里找到同一条，逐字比对。

通过标准：文字完全一致，发送者正确，时间正确。

对不上的常见原因：`text_factory` 没设导致乱码、`local_type` 没取低 32 位、
发送者反推表没建全。三种都会让「看起来有数据」但内容是错的。

## 二、媒体层验收

四类媒体**各抽一条**实际打开，加一个边界用例。逐项过：

| 类型 | 抽什么 | 通过标准 |
|---|---|---|
| 图片 | 普通 JPEG 一张 + wxgf 一张 | 完整原图（段链到 EOI）；尺寸明显大于缩略图 |
| 表情 | 近 3 个月内的一个 | 是 GIF 且能循环播放 |
| 视频 | 一条在客户端播放过的 | 能播，且**进度条能拖动** |
| 文件 | 一条文件名里带空格的 | 按解码后的名字能打开 |
| 视频号 | 一条作品卡片 | 昵称、文案、封面都对 |
| 边界 | 一条本机没缓存原图的 | 显示占位与提示，而不是空白或报错 |

两条容易被忽略的：

- **图片要跟缩略图比尺寸**。解出来能显示不算通过——可能拿到的是缩略图。尺寸差一个量级才算对；
- **视频必须试拖进度条**。能播但拖不动，说明 Range 没做，用户会认为视频坏了。

## 三、界面层验收

### 3.1 渲染级目视核验（强制）

**不能只读 HTML 源码就宣称样式正常。** 样式问题只有在渲染出来才看得见。

无头浏览器截图，然后**读图**检查：

```bash
"<Edge 可执行文件>" \
  --headless --disable-gpu \
  --screenshot=out.png \
  --window-size=1280,3000 \
  --virtual-time-budget=8000 \
  --user-data-dir=<一个独立临时目录> \
  "file:///<页面路径或本地地址>"
```

参数说明：

| 参数 | 作用 |
|---|---|
| `--window-size` | 高度给足，一屏截全，避免分多次截 |
| `--virtual-time-budget` | 等待渲染与异步数据完成，给少了会截到空白 |
| `--user-data-dir` | 用独立目录，避免污染日常浏览器配置 |

截图后逐项检查：**表格是否对齐、文字是否清晰、有无错位、重叠、截断、溢出**。
发现问题就改，改完重新截图，不要凭猜想判断修好了。

### 3.2 交互验收

静态截图看不到的，要实际点一遍：

- 打开会话 → **是否停在最新消息**（这是踩过的坑，见 `05-frontend-layout.md`）；
- 「加载更早」→ 内容接得上，滚动位置不跳；
- 点图片 → 灯箱打开，方向键与滚轮能翻页，张数指示正确；
- 点文件卡片 → 系统默认程序能打开；
- 窄屏（缩到 1024px 以下）→ 导航可用，表格不横向溢出。

### 3.3 控制台无错误

打开页面时浏览器的控制台应当是干净的。
出现 404 通常意味着某个资源路径拼错了；出现 500 要看服务端日志。

## 四、端到端复跑

搭完之后，**清掉产物重跑一遍**，确认流程可重复：

1. 清空解密产物与缓存（不删原始数据）；
2. 重跑提取 → 解密 → 导入 → 打开页面；
3. 每一步的结果与第一次一致。

同时确认一条硬约束：**全程没有改动微信目录**。
对比运行前后微信目录的修改时间，或对关键文件算一次哈希比对。

如果重跑会失败、或者结果不一致，说明流程里藏着只能跑一次的东西
（比如没有跳过已存在的文件、或者状态写在内存里），要修掉。

## 五、失败时的回退

| 现象 | 先查 | 再查 |
|---|---|---|
| 密钥取不到 | 微信是否**正在运行**且登录的是目标账号 | 掩码与正则是否需要随版本更新 |
| 解密后文件头不对 | 保留区大小是否写错（每页尾 80 字节） | 密钥是否真的校验过 |
| 有数据但内容是乱码 | `text_factory` 是否设为 bytes | 内容是否为 zstd 压缩未解 |
| 消息类型全是怪数字 | `local_type` 是否取了低 32 位 | — |
| 图片全是糊的 | 附件候选顺序是否 `.dat` → `_h.dat` → `_t.dat` | 解密缓存是否按同序查 |
| 部分图片打不开 | 是否为 wxgf 容器 | 解码是否用了异步调用 |
| 视频能播但拖不动 | 接口是否支持 Range | 是否返回了正确的状态码 |
| 改了代码页面没变化 | 前端是否重新构建过 | 资源 URL 是否带版本号 |
| 找不到某条消息的文件 | 文件名是否做了 HTML 实体解码 | 该文件本机是否下载过 |

**回退到上一层再验**，不要在当前层反复试。比如「图片显示不对」先回到「附件候选顺序」，
而不是改前端样式。

---

## 完成标志

四道验收都过：数据层数量与内容正确、四类媒体可打开、界面渲染与交互正常、清空后可重跑且未动微信目录。

到这一步，工作台就能交给用户用了。剩下的是按他的实际使用习惯微调——
这一步只能靠他用起来之后反馈，验收替不了。
