# 08 · 环境差异与必经步骤

> 一句话：**方法稳定，参数不稳定。**
> 凡是「值」（路径、密钥、键、目录层级）都必须现场探测，禁止从文档里抄；
> 凡是「步骤」都有必做与可选之分，不做会静默丢数据。
>
> 本篇回答两个高频问题：
> ① 为什么照着文档做，还是卡住？——多半是把「值」当成了常量。
> ② 这一步是不是每台机器都要做？——看下面的判定表。

---

## 一、这一步是不是必经的

| 环节 | 是否必经 | 不做的后果 |
|---|---|---|
| 只读快照 → 在副本上解密 | **必经** | 直接对源库解密会与微信争锁，且违反只读边界 |
| 三库解密（message / contact / session） | **必经** | 没有消息、没有会话名、没有联系人 |
| WAL 合并 | **条件必经**：源目录存在 `-wal` 且帧头合法 | 最近一段消息整段丢失，且**看不出来丢了**（数量对不上才发现） |
| `message_resource.db` | **有媒体则必经** | 资源明细缺失，部分媒体定位不到 |
| `hardlink.db` | **有媒体则必经** | 图片/视频/文件全部没有本地文件对应关系（实测最容易漏的一个） |
| `Name2Id` 发送人映射 | **必经** | 发送人错乱或显示成 `#编号`，群聊几乎不可读 |
| 图片密钥 | **要看图则必经** | 图片全部占位。取不到就**如实标注**，不要用错密钥硬解 |
| wxgf 解码（`VoipEngine.dll`） | **有条件必经**：样本里存在 `wxgf` 头 | 这部分图永远打不开（实测占比可达图片消息的 6%~30%） |
| 链接卡片缩略图 | 可选，但成本极低 | 卡片只有文字，没有预览图 |
| 动画表情、语音转写、视频号封面 | 可选 | 对应类型显示占位 |

**判断口径**：先抽样统计类型分布与容器格式，再决定做不做。
不要因为「文档里写了」就全做，也不要因为「看起来少」就不做——先统计，再决定。

---

## 二、这些「值」因机器而异，禁止硬编码

| 值 | 从哪来 | 为什么会变 | 怎么探 |
|---|---|---|---|
| 微信安装路径与版本号 | 进程可执行文件路径 | 用户可能装在 D 盘、自定义目录 | `Get-Process` 取 Path，或看安装根目录下的版本子目录 |
| 数据根目录 | 微信「设置 → 文件管理」，或配置里的自定义路径 | 用户可以改到任意盘 | 先读配置定位根，再列账号目录 |
| 账号目录名 | `<数据根>/xwechat_files/<账号标识>` | 每个账号不同，可能带后缀 | 列目录，挑出有 `db_storage` 的那个 |
| 数据库密钥 | 微信进程内存 | **每个库独立一把**，登录状态/版本变化可能变 | 取到后落盘缓存，失效再取 |
| 图片密钥 | 进程内存（堆） | 点开图片才驻留；换账号会变 | 取不到就按 03 的 1.5.2 扫堆 |
| 图片尾部 XOR key | 由 JPEG 尾部反推，或 0–255 穷举 | 账号级，可能随版本变 | 见 03 的 1.5、1.5.3 |
| 消息库分片数 | `message/` 目录 | 由消息量决定，可能只有一个 `message_0.db` | 列目录 |
| attach 目录层级 | 实际遍历 | 版本之间层级不同，可能多一层 `Img/Thumb` | 先 `find` 打一层样本，别照抄 |
| cache 缩略图路径 | 实际遍历 | 含 `年-月` 目录，随月份新增 | 见 03 的 1.8 |
| 库表结构 | `PRAGMA table_info` | 升级会加列，列名可能变 | 每次升级后重新确认 |

**原则**：把这些值全部收进一个配置文件；代码里出现字面量路径、字面量密钥，都算缺陷。

## 三、换一台机器，先跑这条最短验证链

不写界面、不建业务库，只验证「能读到东西」。**任何一环不过，先解决它，不要往下铺功能。**

| # | 动作 | 通过标准 |
|---|---|---|
| 1 | 定位数据根与目标账号 | 找到 `db_storage`，账号由用户确认 |
| 2 | 取三个核心库的密钥 | 每把密钥都通过 HMAC 校验 |
| 3 | 解一个库，数表 | 文件头是 `SQLite format 3`，表数量与预期同量级 |
| 4 | 读一个会话的 10 条文本 | 内容可读、发送人能对上号 |
| 5 | 在微信里点开 2–3 张图，再取图片密钥 | 至少一张图能完整打开 |
| 6 | 统计类型与格式分布 | 知道图片里 JPEG/PNG/wxgf 各占多少 |

跑完这六步再谈界面。跳过它们直接做页面，会在「图片全打不开」「发送人全是编号」上返工。

## 四、看起来像「代码写错了」，其实是环境不同

| 现象 | 真实原因 | 处理 |
|---|---|---|
| 图片密钥怎么扫都扫不到 | 密钥不在可打印串里；或图没在客户端点开过 | 按 16 字节对齐扫堆；先点开图片 |
| 文档给的派生式算不出密钥 | 该版本不按此派生，或 seed 未驻留 | 以「能否完整解图」为准，不要卡在派生式 |
| `VoipEngine.dll` 调用返回负数 | 参数个数不对（4 vs 5）或数据被拒 | 看返回码区分，见 03 的 1.4 |
| wxgf 解码「成功」但图是噪点 | 尾部 XOR key 错，解码器容忍坏数据 | 穷举 + 目视 |
| 照着文档的目录结构找不到文件 | 版本间层级不同 | 用 `find` 打样本，按实际结构写 |
| 某台机器根本没有 `hardlink.db` | 版本或安装差异 | 没有就退化为「只显示能定位的媒体」，并说明覆盖率 |
| 同一份脚本，两台机器一个能跑一个不能 | Python 版本/依赖差异 | 依赖装在项目内，别指望系统 Python |

## 五、给用户的预期管理（可直接照说）

> 每台电脑的微信版本、安装位置、缓存策略都可能不同，所以这套东西**不能打包成一个安装包**。
> 我会先在你机器上做六步验证：能不能定位数据、能不能解密、能不能读到消息、
> 能不能看到图片。六步都过了，再谈界面。
> 其中「能看多少张图」不由程序决定，而由微信本机缓存决定——没点开过的图，本机就没有原图。
